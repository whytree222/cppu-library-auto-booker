# 图书馆自动预约（Android v0.19.0）

仅通过可信校园网络直连 `http://mlib.cppu.edu.cn`。自 v0.17.0 起按用户要求移除 WebVPN 校外访问、统一认证、两套账号管理、网址转换和相关验证码 OCR 组件；没有校外备用线路。保留图书馆账号的本机加密保存与过期后自动重新登录。

> 本项目是非学校官方应用，仅供个人学习与测试使用。请遵守学校图书馆的预约规则和学校相关规定；未来商业化前必须确认学校许可。

## 安装与升级

支持 Android 8.0 及以上。GitHub 同版本同步发布；Gitee 作为国内推荐下载，只用于发布安装包和更新信息，源码与说明仍以本 GitHub 仓库为准。Gitee 发布仓库配置完成后，维护者会补充发布页链接和安装二维码。

- **Gitee 最新发布页（国内推荐）**：发布仓库配置完成后由维护者公布链接和二维码。
- **GitHub 最新发布（备用）**：[whytree222/cppu-library-auto-booker/releases/latest](https://github.com/whytree222/cppu-library-auto-booker/releases/latest)
- 微信内置浏览器会拦截 APK 下载：请点右上角“…”→“在浏览器打开”。
- 首次安装需要在系统设置中允许“安装未知应用”；安装后请在“权限”页检查精确闹钟、通知、电池优化和厂商自启动限制。
- 发布页和 `update.json` 会提供 SHA-256，可自行核对下载文件；应用内下载也会自动校验。

**从 v0.18.0 升级到 v0.19.0 必须先卸载旧版再安装。** v0.18.0 由 CI 的临时调试密钥签名，无法用新的固定发布签名覆盖安装。卸载会清除本机的图书馆账号密文、任务、设置、记录和系统权限；学校系统中的预约记录不受影响。从 v0.19.0 起使用固定发布签名，后续版本可直接覆盖升级并保留本机数据。

从 v0.16.x 或更早版本首次升级会取消旧的自定义/多时间预约计划，清除已退役 WebVPN 的账号密文、对应密钥和设置。不会删除直连图书馆账号、座位、使用时段或学校预约记录；不会清空整个 WebView Cookie 库。旧版迁移后需重新核对设置并安排预约；从 v0.17.0 升级则保留原有 00:58 计划。升级本身不会自动创建新任务。旧版本代码可从 Git 历史或 v0.16.0 恢复。

## 应用内更新（v0.19.0）

应用在启动或回到前台时检查一次新版本，正常情况下每天最多检查一次；检查失败会在 1 小时后重试。也可以在“权限”页底部的更新卡片手动检查，手动检查不受每日频率限制。

1. 发现新版本后显示版本号、大小和更新说明；**不会自动下载，也不会自动安装**。
2. 点击“下载更新”后，应用从 Gitee 下载并自动校验大小、SHA-256、包名、版本号和签名证书；Gitee 不可用时切换 GitHub 同版本文件。任一校验不符都会删除文件并拒绝安装。
3. 下载完成后交给 Android 系统安装器，由用户确认覆盖安装；如果尚未允许安装未知应用，会先打开系统授权页。应用无法绕过系统确认，也不承诺静默安装。
4. 更新永不打断预约：预约服务运行中、任务处于运行/触发状态、15 分钟内有待执行任务、停留在登录页或首次权限引导时，不检查、不下载、不安装；预约结束后恢复。
5. 更新检查只读取版本信息，不采集预约内容、账号或座位数据。更新失败时可以重试，或打开 Gitee/GitHub 发布页手动下载。

从 v0.19.0 起，后续版本才能通过应用内更新覆盖安装。更新只在打开应用时检查，不做后台常驻或推送，避免被厂商省电策略杀掉。


## 品牌权限适配（v0.19.0）

权限页会读取本机品牌，按小米/Redmi、华为、荣耀、OPPO、一加/realme、vivo/iQOO、三星、魅族等分别显示自启动、省电策略和后台限制的设置路径；未识别品牌显示通用步骤。页面名称可能随系统版本变化，完成设置后返回应用会自动刷新授权状态。厂商设置仍可能拦截后台运行，应用无法绕过系统限制。

本轮仍不修改预约、调度、登录和提交逻辑。

## 界面改版（v0.18.0）

本轮只调整前端界面，预约、调度、登录和本地存储逻辑未变。预约页按任务摘要、登录与准备、房间座位、日期时段和操作区重新组织，任务状态与下次启动时间只显示一次。房间座位、日期时段、直接与定时预约、权限页、记录页和底部导航统一为 Material 3 组件；停止与取消只在对应状态出现，运行中不会提供重复启动操作。权限页区分必要权限、建议项和默认折叠的高级诊断；记录页按单条任务卡片展示，继续保留最近三次。新增独立深色配色、系统字体缩放适配和切换页面时保留状态的底部导航。

## 直接预约结果弹窗（v0.17.5）

点击“直接预约”后，本次任务的最终反馈会在应用内弹窗显示；设置错误、服务启动失败也直接说明原因。弹窗保留学校返回的详细结果，长内容可滚动、可选取文字，关闭不会重发预约。运行步骤仍在“记录”页。

只关联本次直接预约的任务编号，不弹旧记录或定时任务。已选座、已提交、前四段成功正在追加等中间步骤不当作整笔成功；超时、服务中断和不明确结果提示到学校系统核对。不申请悬浮窗权限，不强行拉起后台界面。

## 使用方法

底部仍为三个独立页面：

- **预约**：检查校园网直连登录，按楼层选择阅览室，在真实座位图中点击候选，再选择使用日期和时段。
- **权限**：精确闹钟、通知、省电及厂商自启动检查，按品牌显示设置路径；提供独立的 60 秒唤醒测试。测试不会预约。页面底部是应用更新卡片。
- **记录**：最近三次任务及可展开的完整步骤，超出自动移除最早一组。

确认选择后，可用两个独立入口：

- **直接预约**：立即按现在的今天/明天和当前所选房间、候选座位、使用时段尝试真实预约，不等待 00:58，也不等待尚未开放；不需要精确闹钟权限。采用本次选择的不可变快照，不覆盖已保存的定时计划或其座位/时段。运行中不并发启动第二个任务。提交结果不明仍停止，不重复提交。
- **预约 · 下次 00:58 启动**：按手机本地时间安排下一次 00:58，今天该时间已过则安排至次日；每次点击只安排一次，不每天循环，也不立即提交学校预约。重复点击替换等待中的计划，不叠加多个抢座时间。可取消等待计划或停止正在运行的任务；不会取消学校已成功的预约。

**直接预约的今天/明天以点击当天为准；定时预约以计划启动当天为基准。** 两个预计使用日期分别显示。 例如 10 月 22 日白天点击预约，下一次启动是 10 月 23 日 00:58；选择“今天”使用日为 10 月 23 日，“明天”则为 10 月 24 日。应用会显示预计使用日期，请核对后再点击。

保留直接预约；不恢复自定义抢座时间、多个时间和演练入口。两个预约入口均为真实预约。固定时段房间仍选择 1–4 个连续使用时段，自选时间房间仍填写开始和结束时间。这些是座位的使用时间，不是抢座启动时间，不能省略。

## 等待与安全规则

00:58 定时任务实际启动后最多运行十分钟；直接预约不启用这段尚未开放等待。学校明确提示“未到可预约时间”等尚未开放状态时，串行定时检查接口（不重复下载整个网页）；开放后继续原有选日、选时段、选座和确认流程。网络慢会降低实际检查频率。成功即结束；网络、账号、参数错误、服务器限流或其他业务拒绝不当作未开放无限重试。提交后结果不明时停止，提示核对学校记录，不能视为成功，也不会盲目重复提交。

只有过刊已核对的七段规则支持“前四段成功后同一座位追加后三段”，两笔共用等待上限；不把过刊布局或时段套给其他房间。

## 座位图与后台限制

内置 2026-10-21 从学校正常页面采集的一至四层七间房布局，共 962 个标记，其中三个无编号。保留原始大小写和行列；重复、异常、无编号位置禁选。地图不是实时空闲状态，运行时重新核对学校页面，布局或座位身份变化则停止。

锁屏运行仍依赖系统按时投递闹钟、后台服务权限及当时可用的校园网络。精确闹钟权限不保证一定秒级准点；小米等设备还需检查自启动和无限制省电。默认 00:58 和十分钟等待不能弥补首次唤醒延迟或断网。直连站点使用 HTTP，不应在不可信网络发送密码。

## 验证与构建

网页回归使用 Node.js 的模拟 DOM，不访问学校系统。包括报刊阅览区 2026-10-24 实际时间差异、分日期同步、未选变化、所选变化仍停止及隐藏旧勾选防护。Android 单元和 Compose 测试覆盖刷新目标、跨日失效、45 秒超时、退出取消、精确时间保留及规则变化、直接与定时入口分离、手动快照不覆盖定时计划、两种日期基准、固定 00:58 策略、一次性消耗、旧配置迁移、直连登录状态、权限页、记录页、地图，以及更新清单校验、重定向白名单、下载哈希、签名校验、预约安全闸门和更新界面各状态。Node 测试额外覆盖版本/发布配置、`update.json` 生成、Gitee 发布幂等和公开下载校验。

GitHub Actions 使用 JDK 17、SDK 35、Gradle 8.9。推送 `main` 只运行测试和未签名 release 构建，不创建或修改任何 Release；只有手动推送 `v*` tag 或带 `publish=true` 的手动运行才使用固定发布密钥签名并同步发布 Gitee 与 GitHub。

测试通过不代表手机锁屏网络、系统安装器或学校当前业务规则一定允许预约。请核对应用中的明确结果与学校“我的预约”记录。

## 发布新版本（维护者）

发布链路使用同一份 `version.properties`、同一个签名 APK、同一份 `update.json` 和 SHA-256，同步创建 Gitee 与 GitHub Release。Gitee 只保存 Release 和客户端读取的 `update.json`，不镜像源码。

1. 修改 `version.properties`（`versionCode`、`versionName`、`minSupportedVersionCode`），并新增 `release-notes/<version>.md`。
2. 运行 Node 与 Android 测试：`npm ci && npm test`、`gradle testDebugUnitTest`。
3. 确认 GitHub Secrets：`ANDROID_KEYSTORE_BASE64`、`ANDROID_KEYSTORE_PASSWORD`、`ANDROID_KEY_ALIAS`、`ANDROID_KEY_PASSWORD`、`GITEE_TOKEN`；Repository Variable：`RELEASE_CERT_SHA256`。`GITEE_TOKEN` 需要 `projects` 权限，且不得写入代码、日志或 `distribution.properties`。
4. 确认公开 Gitee 仓库 `cppu-library-auto-booker-release` 的 `main` 分支存在，把 Gitee 用户名填入 `distribution.properties` 的 `giteeOwner`，运行 `npm run release:qr` 生成 `docs/download-qr.png`，并把发布页链接和二维码补回上方“安装与升级”。
5. 手动运行 GitHub Actions，保持 `publish=false`，检查签名、版本号、`dist/update.json`、`dist/sha256sums.txt`。
6. 确认无误后推送 tag：`git tag v0.19.0 && git push origin v0.19.0`。工作流只在 tag 等于 `version.properties` 的版本时发布；版本冲突会失败，不覆盖历史 Release。
7. 发布后检查 Gitee/GitHub 两个发布页、两个 manifest 和两个 APK 的大小/SHA-256 一致，并在真机完成安装和预约回归。

发布密钥必须离线备份。丢失密钥后无法继续覆盖升级，只能让用户卸载重装；keystore、密码和 token 不能提交到仓库。`distribution.properties` 只放公开信息。CI 发布失败时只会删除本次新建的 GitHub 草稿 Release，不修改或删除历史 Release 和 tag。

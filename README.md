# 图书馆自动预约（Android v0.20.3）

v0.20.3 更新：修复 WebVPN 已登录却在“正在选择使用日”停住的问题，避免代理页面的表单地址反复改写；增加选日、选时段等步骤的独立超时和具体错误提示。校园网直连优先，预约提交前遇到直连网络故障时可单向切换学校 WebVPN。WebVPN 使用原生应用表单，先输入统一认证账号、密码和验证码，再登录图书馆；验证码仅手动输入，不自动识别或点击学校网页。可明确选择在本机加密记住两套账号密码。提交结果不明时不换线路、不重新登录、不重发；图书馆直连账号的自动重新登录保持原样。

> 本项目是非学校官方应用，仅供个人学习与测试使用。请遵守学校图书馆的预约规则和学校相关规定；未来商业化前必须确认学校许可。

> 维护者与自动化代理：工程约束、构建测试、发版与故障恢复见 [AGENTS.md](AGENTS.md)。

## 开发中的原生全流程自动登录（调试包，尚未正式发布）

本轮开发在已修复的原生登录接口上增加自动恢复，不再使用隐藏网页点击或定位验证码元素。两套 WebVPN 账号均已保存并开启时，默认启用全流程自动登录；可在账号页关闭，关闭后的选择会保留。统一认证与图书馆账号仍独立加密保存，暂停状态不会被升级清除。

- 打开应用、主动检查及直接／定时预约需要 WebVPN 时，先复用有效会话；过期才获取学校当前表单，在本机识别验证码并完成两层登录，不增加常驻轮询。
- 每轮最多 90 秒、三张验证码；只在识别不可靠或学校明确提示验证码错误时，间隔至少 1.5 秒换图重试。每张表单最多提交一次，图书馆每轮最多登录一次。
- 账号拒绝、限流、额外认证及结果不明均停止；验证码耗尽后冷却五分钟，账号拒绝或可能已提交的未知结果暂停对应账号自动恢复。保留应用内手动登录入口。
- 自动与手动登录共享独占会话，接管前等待旧请求及 Cookie 写入收尾；已有预约执行期间不会开启新的手动认证。预约提交后不重登、不重发，十分钟等待截止时间不重置。
- 图片、识别结果和认证动态字段只在内存中使用。先交付独立调试包，正式发布另行确认；调试版与正式版的数据不共享，真机和隔夜效果仍需验证。

## 应用内更新（v0.19.0）

应用在启动或回到前台时检查一次新版本，正常情况下每天最多检查一次；检查失败会在 1 小时后重试。也可以在“权限”页底部的更新卡片手动检查，手动检查不受每日频率限制。

1. 发现新版本后显示版本号、大小和更新说明；**不会自动下载，也不会自动安装**。
2. 点击“下载更新”后，应用从 Gitee 下载并自动校验大小、SHA-256、包名、版本号和签名证书；Gitee 不可用时切换 GitHub 同版本文件。任一校验不符都会删除文件并拒绝安装。
3. 下载完成后交给 Android 系统安装器，由用户确认覆盖安装；如果尚未允许安装未知应用，会先打开系统授权页。应用无法绕过系统确认，也不承诺静默安装。
4. 更新永不打断预约：预约服务运行中、任务处于运行/触发状态、15 分钟内有待执行任务、停留在登录页或首次权限引导时，不检查、不下载、不安装；预约结束后恢复。
5. 更新检查只读取版本信息，不采集预约内容、账号或座位数据。更新失败时可以重试，或使用上方固定链接手动下载（应用内更新仍使用版本化 APK 地址和签名校验，不依赖固定文件名）。

从 v0.19.0 起，后续版本才能通过应用内更新覆盖安装。更新只在打开应用时检查，不做后台常驻或推送，避免被厂商省电策略杀掉。

## 已发布 v0.20.3 的 WebVPN 校外备用（应用内手动验证码）

在预约页点击“WebVPN 应用内登录”，在应用原生表单中完成认证。页面不会显示学校网站，也不再需要“更多操作”或重复点击网页登录。

- **只走学校 WebVPN**：仅使用 `https://webvpn.cppu.edu.cn` 的图书馆代理路径；不使用第三方代理、公共镜像或自建转换服务。
- **直连优先、单向切换**：预约先走校园网直连；只有提交预约前出现 DNS、连接、超时或网关故障时才切换到 WebVPN。切换后本次任务只继续使用 WebVPN，不会自动切回。
- **提交后不重发**：一旦进入提交阶段，结果不明或网络中断都会停止并提示核对学校记录，不会换线路、换座位、重新登录或重复提交。
- **第一步：统一认证**：应用显示学校当前会话的验证码图片，你填写学工号、统一认证密码和四位数字验证码，再点击“登录统一认证”。可勾选学校的“五天内自动登录”；具体有效期仍由学校决定。
- **第二步：图书馆**：统一认证验证通过后，应用显示独立的图书馆账号密码输入框，点击“登录图书馆”；两层均经学校验证后才返回主界面。
- **手动验证码**：图片只保存在内存，支持换图。输入错误或学校明确拒绝后，显示新验证码，仍需你点击登录；不会自动识别、连续点击或重复发送旧表单。
- **记住账号可选**：两套密码分别在本机使用 AES/GCM + AndroidKeyStore 加密，只有勾选后才保存。密码、验证码、动态参数不会写入日志或页面恢复状态。
- **过期后需要你操作**：统一认证过期时，应用提示打开应用内登录并补输验证码，不再后台自动识别和提交统一认证。已有 WebVPN 会话有效时，后台预约继续使用；仅图书馆内层过期且已保存开启其账号时，保留内层自动重登。
- **未知结果先检查**：网络在提交后中断时停止，不自动重新发送；使用“检查登录状态”只读核对，或者由你明确重新获取表单。
- **定时规则不变**：仍是下一次本地 00:58 的一次性精确闹钟，触发后最多等待学校开放 10 分钟；切换线路或重新登录不会重置等待截止时间。
- **采集页限制**：房间和座位采集页仍使用校园网直连；校外可预约已有房间、候选座位和本地时段。
- **验证范围**：原生表单、编码、会话绑定、认证回跳和提交保护已做本地模拟测试。2026-10-27 用户反馈 E 调试版登录问题已解决，10-28 反馈选日修复测试包可用；不代表已验证新正式签名包、五天会话、锁屏或隔夜预约。

WebVPN 地址转换按 [webvpn-converter](https://github.com/WilliamPeterMatthew/webvpn-converter) 的 AES-CFB 规则在本机生成，不联网转换网址。

## 使用方法

底部仍为三个独立页面：

- **预约**：检查校园网直连登录，直连不可用时可使用外层认证仍有效的 WebVPN 备用；按楼层选择阅览室，在真实座位图中点击候选，再选择使用日期和时段。
- **权限**：精确闹钟、通知、省电及厂商自启动检查，按品牌显示设置路径；提供独立的 60 秒唤醒测试。测试不会预约。页面底部是应用更新卡片。
- **记录**：最近三次任务及可展开的完整步骤，超出自动移除最早一组。

确认选择后，可用两个独立入口：

- **直接预约**：立即按现在的今天/明天和当前所选房间、候选座位、使用时段尝试真实预约，不等待 00:58，也不等待尚未开放；不需要精确闹钟权限。采用本次选择的不可变快照，不覆盖已保存的定时计划或其座位/时段。运行中不并发启动第二个任务。提交结果不明仍停止，不重复提交。
- **预约 · 下次 00:58 启动**：按手机本地时间安排下一次 00:58，今天该时间已过则安排至次日；每次点击只安排一次，不每天循环，也不立即提交学校预约。重复点击替换等待中的计划，不叠加多个抢座时间。可取消等待计划或停止正在运行的任务；不会取消学校已成功的预约。

**直接预约的今天/明天以点击当天为准；定时预约以计划启动当天为基准。** 两个预计使用日期分别显示。 例如 10 月 22 日白天点击预约，下一次启动是 10 月 23 日 00:58；选择“今天”使用日为 10 月 23 日，“明天”则为 10 月 24 日。应用会显示预计使用日期，请核对后再点击。

保留直接预约；不恢复自定义抢座时间、多个时间和演练入口。两个预约入口均为真实预约。固定时段房间仍选择 1–4 个连续使用时段，自选时间房间仍填写开始和结束时间。这些是座位的使用时间，不是抢座启动时间，不能省略。

## 等待与安全规则

00:58 定时任务实际启动后最多运行十分钟；直接预约不启用这段尚未开放等待。学校明确提示“未到可预约时间”等尚未开放状态时，串行定时检查接口（不重复下载整个网页）；开放后继续原有选日、选时段、选座和确认流程。网络慢会降低实际检查频率。成功即结束；网络、账号、参数错误、服务器限流或其他业务拒绝不当作未开放无限重试。提交后结果不明时停止，提示核对学校记录，不能视为成功，也不会盲目重复提交。

只有过刊已核对的七段规则支持“前四段成功后同一座位追加后三段”，两笔共用等待上限；不把过刊布局或时段套给其他房间。

## 发布新版本（维护者）

发布链路使用同一份 `version.properties`、同一个签名 APK、同一份 `update.json` 和 SHA-256，同步创建 Gitee 与 GitHub Release。Gitee 只保存 Release 和客户端读取的 `update.json`，不镜像源码。

首次发布前，在一台可信电脑上生成固定发布密钥并离线备份（只需一次，不能提交到仓库）：

```bash
keytool -genkeypair -v -keystore cppu-release.jks -alias cppu-library \
  -keyalg RSA -keysize 4096 -validity 10000
base64 -w0 cppu-release.jks > cppu-release.jks.base64
keytool -list -v -keystore cppu-release.jks -alias cppu-library
```

把 `.jks.base64` 的内容、keystore 密码、别名 `cppu-library` 和密钥密码分别填入对应的 GitHub Secrets；`keytool` 输出中的 SHA-256 填入 `RELEASE_CERT_SHA256`（Windows 可用 PowerShell：`[Convert]::ToBase64String([IO.File]::ReadAllBytes('cppu-release.jks'))`）。密钥或密码丢失后，已安装用户无法覆盖升级，只能卸载重装。

1. 修改 `version.properties`（`versionCode`、`versionName`、`minSupportedVersionCode`），并新增 `release-notes/<version>.md`。
2. 运行 Node 与 Android 测试：`npm ci && npm test`、`gradle testDebugUnitTest`。
3. 确认 GitHub Secrets：`ANDROID_KEYSTORE_BASE64`、`ANDROID_KEYSTORE_PASSWORD`、`ANDROID_KEY_ALIAS`、`ANDROID_KEY_PASSWORD`、`GITEE_TOKEN`；Repository Variable：`RELEASE_CERT_SHA256`。`GITEE_TOKEN` 需要 `projects` 权限，且不得写入代码、日志或 `distribution.properties`。
4. 确认公开 Gitee 仓库 `whytree/cppu-library-auto-booker-release` 的默认分支为 `master` 且至少有一个提交（空仓库先在网页新建一个文件建立 `master`）；创建勾选 `projects` 权限的私人令牌并填入 `GITEE_TOKEN`。仓库地址或分支变化时修改 `distribution.properties` 的 `giteeOwner`/`giteeBranch`，运行 `npm run release:qr` 重新生成 `docs/download-qr.png`（Gitee）和 `docs/download-qr-github.png`（GitHub），并更新上方“安装与升级”的链接和图片。固定下载链接不随版本变化，正常发版不需要重新生成二维码。
5. 手动运行 GitHub Actions，保持 `publish=false`，检查签名、版本号、`dist/update.json`、`dist/sha256sums.txt`。
6. 确认无误后推送 tag：`git tag v0.19.1 && git push origin v0.19.1`。工作流只在 tag 等于 `version.properties` 的版本时发布；版本冲突会失败，不覆盖历史 Release。
7. 发布后检查两个固定下载链接、两个发布页、两个 manifest 和两个 APK 的大小/SHA-256 一致，并在真机完成安装和预约回归。固定链接返回的 `library-auto-booker.apk` 应与版本化 APK 字节相同。若某个已有 Release 缺少固定别名，手动运行 `Backfill fixed download alias` 工作流并填入对应 tag；它只新增固定别名并校验哈希，不创建、修改或删除 Release，也不能覆盖已有资产。

发布密钥必须离线备份。丢失密钥后无法继续覆盖升级，只能让用户卸载重装；keystore、密码和 token 不能提交到仓库。`distribution.properties` 只放公开信息。CI 发布失败时只会删除本次新建的 GitHub 草稿 Release，不修改或删除历史 Release 和 tag。

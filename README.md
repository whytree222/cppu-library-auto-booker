# 警察大学图书馆自动预约（Android）

本项目面向校内预约站点 `http://mlib.cppu.edu.cn` 的过刊阅览室。可以前一晚按优先级输入座位号，选择今天或明天以及七个固定时段中的连续 1–4 段，再设置下一次放号时间。应用届时启动前台任务，依输入顺序查找可预约座位并尝试预约。

## 安装

从 [GitHub Releases](https://github.com/whytree222/cppu-library-auto-booker/releases) 下载 `app-debug.apk`，安装到 Android 8.0 或更新版本的手机。这是调试签名的侧载版。手机运行任务时必须能通过校园网直连，或通过学校 WebVPN 访问图书馆。

## 使用

1. 连接校园局域网，打开应用会先检查登录状态，有效时自动进入主界面。确认过期后显示登录页，填写学校账号密码并点“登录并进入应用”。“自动重新登录”首次默认勾选，学校验证成功后才加密保存；取消勾选则不保存密码，并删除原有保存信息。已启用自动重新登录时先尝试恢复会话，成功后自动进入。也可使用学校网页登录。
2. 在“座位号”输入框每行填一个编号，第一行优先。例如 `G015A`。最多 10 个，重复编号会自动去重。
3. 填写实际放号时间，点“今天”或“明天”（以任务运行当天为准），再从七个固定时段中选择连续的 1–4 段。保持“演练模式”开启，点“立即演练”，确认应用能依次进入过刊阅览室、选日、选时段和识别座位。演练会导航到座位图，但不会提交预约。
4. 如需预约全天，选择第 1–4 段后开启“同一座位追加后三个时段”。前四段明确成功后，应用会自动重走选日、选时段流程，为实际约到的同一座位预约第 5–7 段。第二笔只尝试这个座位，不换座；两笔锁定同一个使用日期。
5. 演练成功后关闭“演练模式”，开启“下次放号时运行一次”，保存任务并授予精确闹钟及通知权限。也可点“立即运行一次”执行相同的两笔流程。演练只检查第一笔，不提交、不启动第二笔。

预约任务只运行一次，运行后自动关闭。默认处理一笔（最多四个连续时段），开启上述选项后按“前四段 + 后三段”自动提交两笔，每笔仍遵守时段限制。前四段失败或结果不明时，不启动后三段；后三段失败、不可预约、超时或登录失效时，通知会说明“前四段已成功，后三段未确认成功”，保留前四段。仅当两笔都明确成功时才提示全部成功。

若首选座位不可预约，会寻找下一座位；若提交后明确提示座位已被预约，应用会关闭结果提示、清除先前选座，再尝试下一项。开启追加时，第二笔锁定第一笔的成功座位，不使用其他候选。其他失败会显示学校返回的提示。若无法判断提交结果，应用会停止并提示到学校系统核对，避免重复提交。用户仍需按学校规定完成签到。

## 当前适配限制

### 登录状态检查接续恢复、验证码有界自动重试（当前版本 v0.13.6）

此前主页周期检查和状态卡只调用只读验证接口，能显示 WebVPN 已过期，却没有调用两步恢复。现在主页及入口页的前台周期检查、手动检查状态都接上已启用的独立两套账号恢复，不再把“显示已过期”当作流程结束。状态卡显示恢复阶段；未保存开启、识别被关闭或账号因已提交未通过/结果不明而暂停时说明原因，不擅自取消用户关闭和安全暂停。单独维护 WebVPN 备用会话不改掉直连有效状态或抢占首选通道。预约任务运行期间，状态卡只读检查，登录恢复由预约任务自己协调，避免提交过程中另起认证。

验证码不再一次失败就要求点“更多操作”：临时读取失败先自动再读两次；输出不完整、置信信号不足或本机推理失败时，间隔至少 1.5 秒，通过学校原图的 `refreshCaptcha(this)` 点击处理自动换图，最多换两张、最多识别三张不同图片。新图未实际更新时不重复识别旧图，八秒仍未更新则停止。手动输入即停止，不覆盖输入；页面、来源或结构不匹配不刷新，不降低四位数字、原始输出一致和置信门槛。此处自动换图是 v0.13.6 新行为，先前版本“不刷新验证码”的说明不再描述当前有界重试。

统一认证一旦进入提交阶段就停止验证码读取和刷新，仍不因未知结果重发账号密码或预约。两步登录总时限仍为 90 秒，自动换图不重置时限。一次自动恢复失败后，前台状态检查有五分钟冷却，冷却后再自动检查；修改账号配置可重新尝试。预约任务所需的登录恢复不受该状态卡冷却限制，但仍遵守已暂停账号和单次提交保护。应用不在被系统杀掉或未运行时承诺维持会话，不承诺识别必然成功。

新增模拟过期状态触发恢复、取消、备用维护不覆盖直连、冷却、自动换图后识别完成、三张上限、旧图超时、暂停/关闭取消延迟刷新等回归。网页测试与本机控制器测试不代表真实学校登录成功；没有用真实账号代登录，仍需手机前台及定时任务复测。

### 修复“未到可预约时间”提前停止等待（v0.13.5 起）

学校实际返回“当前时间为:00:55:01 未到可预约时间!”。旧版只匹配“未到预约时间”，漏了“可”字，导致明确未开放也被当作普通拒绝并立即停止；这不是截图中闹钟的触发问题，也尚未提交座位预约。现同步修复开放接口检查、日期时段页面提示和明确预约结果三处分类。

开启“未开放时最多等待 10 分钟”后，遇到该明确提示继续串行检查开放状态，开放后继续原有选座流程；十分钟仍从服务实际启动开始计时，反复拒绝、返回检查及追加时段均不重置窗口。比如实际 00:55 启动，窗口约到 01:05；这不是对学校实际放号时间的推断或预约成功保证。未开启等待时仍按原行为停止。

混有登录失效、已有预约、次数限制等提示仍停止，不把这些失败当作未开放。网络、异常响应、限流以及最终提交结果不明等保护未改变，业务拒绝不切换 WebVPN。新增基于截图原文的回归覆盖五分钟后开放、十分钟结束、仅剩两秒窗口、时段页面提示、明确提交拒绝与混合业务拒绝；测试使用模拟时钟与网页，未访问学校系统或真实提交预约。

### 进入网页自动接续两步登录（v0.13.4 起）

已保存并开启两套账号时，打开 WebVPN 网页就启动一轮登录，无需点击“使用已保存账号重新开始”：等待当前网页加载完成，再填写统一认证账号、识别当前验证码、勾选已启用的五天选项并通过学校原按钮提交；学校认证通过后使用独立图书馆账号登录。两层都有效时不再提交登录。

修复启动时序：WebView 提前暴露的网址不再被当作已加载的文档；进入、返回前台和代理跳转都等待真实匹配的页面完成回调。重复完成回调不会重新准备账号、打断验证码或将尚在等待结果的登录误判为失败。初次进入和手动重新开始使用同一个启动入口；后台登录恢复也采用同样的页面就绪判断。

“重新开始”保留为失败后的主动操作，不是正常自动登录的必经按钮。未保存、未开启或已因未知提交结果暂停的账号不会擅自恢复；手动输入、验证码不可靠、网络异常与未知提交结果仍停止，不连续重发。本次新增无需点重启的完整两步、早于网页回调的前台恢复、重复回调与暂停账号等模拟回归测试；没有用真实账号代登录，仍需手机复测。

### 主表单定位、自动提交与五天选项（v0.13.3 起）

只读核对图书馆公开登录页发现：页头 `fromuser1` 和主表单 `fromuser` 都有 `id="user"`，页头密码为 `passwd1`，主表单密码为 `passwd`。旧版按整个文档查用户名数量，导致正常页面被误判。现仅在主表单内定位并填写两套账号设置中的 WebVPN 图书馆凭据，不填写页头；主表单内重复字段或全页重复 `passwd` 仍拒绝，因为学校原编码函数通过全局 `#passwd` 查密码。不会把真实结构错误继续泛称为“账号设置已改变”。

统一认证和验证码的地址绑定改为：先验证目标，再将同一资源的原始/代理表示规范化比较；只改写表示、不改查询参数的变化，不再造成旧结果失效或被当成用户改账号。查询、图片像素、表单节点、输入内容等真实变化仍拒绝旧结果。账号及安全识别的验证码均完成后点击学校原按钮，只尝试一次；先完成验证码、后完成账号准备的顺序也可触发。阶段文字区分等待验证码和等待学校提交结果。模型无法安全识别、手动修改或未知提交结果仍停止，不意味着任意验证码都能自动登录。

“更多操作”新增“自动勾选学校‘五天内自动登录’”，应用户要求默认开启，可关闭且记住设置。仅对已开启的统一认证账号登录应用；在当前密码表单选择已确认的校方选项，兼容移动/桌面隐藏重复控件，不覆盖手动取消或已有手动选择。这个开关控制自动勾选，不强行覆盖校方网页。五天是学校的选项，不是应用承诺；服务器可以提前使会话过期，应用不延长 Cookie。需要时仍会分别检查统一认证和图书馆两层状态。

回归包含校方实际同名主/页头结构、原始代理表示切换、五天选项及手动优先、模拟 DOM 提交事件经模拟校方校验函数触发一次等测试，不代表已测试真实浏览器或学校认证服务器，没有用真实账号代登录。请先打开 WebVPN 在前台验证两步；若仍停住，提供顶部完整提示和是否已自动填验证码（遮住学工号即可，不要发送密码）。截屏仍然可用。

### 修复统一认证原始相对路径（v0.13.2 起）

截图显示“登录表单的代理目标尚未匹配”，这是地址校验阶段，还没有进入模型识别。只读核对校方公开页面后，确认原始表单使用 `action="/tpass/login"`，验证码图片使用 `/tpass/captcha.jpg`。WebVPN 可在 DOM 属性中保留原始根相对路径；旧版将这些属性直接按 WebVPN 门户域名解析，会误判为其他资源。

v0.13.2 仅在已验证的学校 SSO 代理页面将原始 `/tpass/…` 属性按同一个 SSO 资源解析；同时验证实际表单目标和已经加载的图片。若原始相对表单目标尚未改写，只将已验证的 `/tpass/login` 转为对应的 SSO 代理路径并保留查询参数，在填写任何账号密码前再次检查。不会将未知主机、其他代理或其他路径加入白名单；不更改验证码图片地址、不刷新挑战、不替代学校原密码加密和提交函数。定位失败细分为原始地址、实际提交地址、地址转换失败等原因，不暴露查询参数或凭据。

已添加原始/代理 DOM 表示、相对表单转换、查询参数保留、图片不刷新及拒绝外部目标的模拟回归测试；未使用真实学校账号提交认证，仍需用户安装后实测。若仍报错可截图（遮住账号与登录凭据），本版不恢复防截屏限制。

### 恢复截屏（v0.13.1 起）

按用户要求移除应用添加的防截屏限制，直连/WebVPN 网页登录、两套账号设置和本机 OCR 试验页面均允许截屏，方便反馈错误。账号仍加密保存，密码不回显，其他登录和预约逻辑未修改。分享图片前请自行遮住学工号、密码及网址中的登录凭据。本次只恢复截屏，尚未取得具体报错，不能视为已经修复登录失败。

### WebVPN 两步自动登录（v0.13.0 起）

新增“WebVPN 两套账号与自动登录”入口：①学校统一认证学工号/密码，②WebVPN 内图书馆账号/密码。两套凭据分别由 Android Keystore 的独立 AES-GCM 密钥加密，首次默认不保存，需分别勾选同意并点“保存并开启”。不会复制直连账号或混用密码。保存显示“待验证”，只有学校实际验证通过才标记上次验证成功；这不代表会话以后一直有效。可独立关闭、删除或恢复暂停的账号。账号密码不要发在聊天或提交到仓库。

首次设置后点“打开 WebVPN 验证两层登录”：先打开代理图书馆登录页；学校若要求统一认证，应用填入第一套账号，在本机读取当前已经加载的四位数字验证码，并点击学校原来的密码登录按钮，保留 `checkPassLogin()` 的密码加密和校验；认证通过后，使用第二套账号走图书馆原登录流程。两层已有效时不再填写密码。校方页面的“五天内自动登录”仍由用户选择及服务器决定，应用不延长有效期。

本次修复代理脚本下“原始地址”和“WebVPN 代理地址”两种 DOM 属性表示的兼容性，仅允许对应同一个已验证的学校资源，不放宽到其他学校网站。验证码失败会细分为页面/表单定位、代理目标不符、图片无法安全读取等提示。顶部改为精简工具栏，详细说明和试验按钮收起，避开系统状态栏。v0.13.1 已撤掉防截屏限制，账号设置与网页登录均可截屏。

已启用的两套账号也可供定时任务的登录恢复使用，最长一轮 90 秒。密码/验证码未通过、额外校验、页面不支持或提交结果不明会停止，不刷新验证码碰运气、不连续尝试登录；已提交而未确认的相应账号暂停，需用户核对后在账号设置中允许重新尝试。手动输入始终优先，不覆盖已有填写。停止任务会释放其登录订阅，最后一个使用者退出时关闭本轮登录。图片、验证码、Cookie、密码与完整认证地址不记入日志，也不上传识别服务。

预约仍遵守原有保护：直连优先；只有预约提交前的直连传输故障才自动使用 WebVPN，业务拒绝不切换；最终预约提交后结果不明不进行登录恢复、换通道或重发。两步自动登录不能解决手机断网、系统推迟闹钟或后台进程被杀的问题。代码采用模拟账号/网页回归测试，没有用真实学校账号代登录；请先前台测试完整两步，再做锁屏短时测试。

### WebVPN 验证码自动读取与填写（历史版本 v0.12.1）

以下描述只适用于 v0.12.1；当前版本的账号保存与自动提交行为以上节 v0.13.0 为准。

已依据学校公开统一认证页的实际结构适配，使用 v0.12.0 在用户手机上已验证可运行的同一 ddddocr 本地模型。打开“WebVPN 统一认证 / 图书馆网页登录”后，“自动识别并填写验证码”默认勾选，可取消且会记住选择。页面显示验证码后，读取当前已加载的图片、在本机识别，合格结果自动填写到学校原来的验证码输入框；不需要截图导入。输入框识别仅针对 `form#fm1 input#authcode`，图片仅针对同一表单的 `img.codeImg`。只允许精确的 HTTPS 统一认证地址与已验证的 WebVPN SSO 代理路径，不能在任意学校子域或其他表单填写。

**这个版本自动识别和填写验证码，但不自动提交统一认证登录，也不保存、读取或代填统一认证账号密码。** 仍需你在学校页面输入账号密码、核对验证码并点击学校原来的登录按钮；这样保留学校页面的密码加密、登录校验和“五天内自动登录”选择。验证码已填写不代表统一认证成功，也不代表代理内图书馆登录有效；两层登录仍独立检查。后台预约遇到需要统一认证时仍会提示完成网页登录，尚未实现无人值守的统一认证自动重登。保存的直连密码不发送到 SSO 页面。

验证码图片由页面本身正常加载，识别功能不重新请求图片、不自动刷新、不点击登录；约每 800 毫秒读取一次页面状态不是服务器轮询。识别只在登录页前台运行，每个页面/用户主动重试轮次最多处理三张不同图片，观察窗口三分钟；取消勾选、页面跳转、切入后台或关闭后不再填写旧结果。模型识别失败、不完整、数字限定与原始输出不一致，或最弱输出字符的置信信号低于 0.70 时停止自动填写；该门槛不是准确率保证。

填入前再次确认当前页面/表单/输入框/图片身份、地址、尺寸及完整像素一致。你手动输入后不会覆盖，即使随后删空也保留手动优先；需要继续时点“重新识别当前验证码”。你刷新验证码时，仅清除应用自己刚填入且未被你修改的旧结果，再识别当前图片。失败后可随时手动输入；重试按钮不刷新服务器验证码、不清除你的非空手动内容。图片、验证码、页面完整地址、Cookie 或账号密码不写入运行记录和公开仓库。识别中切换到后台会丢弃结果，返回时同一图片可能需要主动点重新识别。

已完成页面读取/填写、来源白名单、手动输入保护、图片/地址/元素更新导致旧结果丢弃等模拟回归测试；没有使用真实账号提交学校认证或预约。完整手机网页登录仍需实测。使用范围仍限学校系统管理方授权的本人账号、个人非商业用途。

### 直连优先、学校 WebVPN 自动备用（v0.11.0）

验证包括转换向量、代理路径与 Cookie 隔离、统一认证/图书馆登录状态区分、单向切换、同步提交锁及代理页面模拟流程。未使用真实账号进行远程登录或预约；学校统一认证及手机移动网络下的完整流程仍需用户实测。WebVPN 不能解决手机系统本身禁止后台联网或首次闹钟延迟的问题。

### 首次权限引导与失败原因（v0.7.0）

首次安装打开（旧版本升级后首次打开也会显示一次）依次说明通知、精确闹钟和后台设置用途，再询问是否开启；已授予的系统权限跳过，未授权可选择暂不开启，首页可重新查看引导。后台自启动和省电策略由用户在系统设置中选择，不假定进入设置即代表授权成功。

座位号按 `G + 三位数字 + 一个字母` 校验，小写自动转大写。格式正确但当前座位图不存在、网页不可预约、服务器确认已被预约分别提示；页面仅标记不可预约时不会断言已被别人预约。学校失败消息按登录、日期时段、重复预约及数量限制分类并保留原提示。超时仍要求核对记录，不自行重发。

### 登录与后台诊断（v0.6.0）

- 首页向学校的 `/isLogin` 验证登录，显示检查时间。回到前台立即检查、前台每分钟检查，也可手动刷新。网络不通显示“无法验证”，不会直接判定退出登录。登录页面验证通过后才自动返回；预约中遇到登录页也会更新失效状态。关闭应用期间不会持续检测登录有效期。
- 首页展示正式安排的完整日期、时间、演练/真实预约模式，以及精确闹钟、通知、省电豁免状态。每次安排、闹钟触发、服务启动、预约阶段和结果都写入本机记录，不记录 Cookie、账号密码或请求正文。通知不可见时仍可在应用内查看。
- 授予精确闹钟权限并返回应用后，会继续安排刚才保存的任务。未来任务在应用更新、手机重启或重新打开应用后重新登记。服务无法启动会留下失败记录；计划时间已过但没有触发记录会明确提示。系统强行停止、厂商限制和校园网络中断仍可能阻止预约，不能仅凭安排成功保证最终触发。
- “60 秒后台唤醒测试”只测试闹钟和前台服务，不访问预约流程，不修改正式任务。点击后锁屏，稍后回应用查看记录。正式任务前 20 分钟禁止安排测试，避免系统对连续空闲闹钟的频率限制影响放号任务。小米设备可从应用提供的系统设置入口检查后台运行、自启动和省电限制；系统省电豁免状态不代表所有厂商限制都已解除。
- 两笔预约沿用上一版流程，后三段失败时保留前四段。

### 网页适配

v0.6.1 校验当前显示的时段卡片，排除隐藏的旧选项，并从完整使用日期或明确的 `isuseday` 相对使用日解析日期。完整日期、相对日和卡片日期冲突时停止；不修改网站原始表单参数。今天、明天及隐藏旧时段均有回归测试。

已确认登录入口是 `/login`、选择流程是 `/selectreadingroom`、座位图是 `/multireadingroomtablelist`。用户提供的开发者工具截图显示过刊阅览室卡片调用 `roomonclick('26')`，使用日由 `selectusedaybuttonclick(...)` 选择，时段由学校网页提供的复选框表单提交；应用不保存或自行生成网页签名参数。座位元素以完整编号为 `id`（例如 `G015A`），用 `available` / `unavailable` 类标记状态。

用户提供的网页函数确认：`layoutBespeak()` 从 `#tableNo` 读取座位，再调用 `commitbesk()`。网站只有在 Alertify 预约确认框点击“确认”后才发送请求。v0.4.4 会核对确认框的座位、日期、时段及房间字段，点击一次确认，并读取 `.ajs-content` 中的成功或失败信息。延迟弹窗也会持续检查。旧版漏掉此确认步骤，可能只打开弹窗而没有发送预约请求。

确认流程已通过模拟网页测试，真实提交仍需在校园网络和有效登录状态下核对学校预约记录。如果任一步找不到或状态不符，应用会停止。不能保证放号瞬间一定抢到座位。

学校登录页目前使用 HTTP。页面对密码进行 Base64 编码，但没有 TLS 传输保护；请只在可信的校园网络中登录。默认只复用本机 WebView 的 Cookie；开启自动登录后保存的账号密码按上文方式加密。不要在公开 Issue 中上传 Cookie、Token、学号或密码。

## 构建

GitHub Actions 使用 JDK 17、Android SDK 35 和 Gradle 8.9 执行 `testDebugUnitTest assembleDebug`，成功后将 APK 放入 Actions Artifact 和 GitHub Release。本机安装相同工具后，也可运行同一命令。输出位于 `app/build/outputs/apk/debug/app-debug.apk`。仓库不包含登录凭据、签名密钥或 Cookie。

确认流程测试使用 Node.js 22：运行 `npm ci --ignore-scripts` 后执行 `npm test`。测试模拟学校确认框及请求回调，不连接学校系统、不创建真实预约；GitHub Actions 在打包前执行这些测试。
